# Работа с репозиторием

## Первый пуш (один раз)

Репозиторий уже инициализирован локально, есть коммит-база. Дальше:

```bash
# создать приватный репозиторий на GitHub и запушить текущую ветку
gh repo create captcha --private --source=. --remote=origin --push

# без gh — создать пустой репо в вебе, потом:
git remote add origin git@github.com:<твой-логин>/captcha.git
git branch -M main
git push -u origin main
```

## Доступ другу

**Приватный репозиторий на бесплатном плане GitHub:**

1. Открыть репозиторий → `Settings` → `Collaborators` → `Add people`.
2. Ввести GitHub-username или e-mail, выбрать роль **Write**.
3. Он принимает приглашение из письма/уведомления — и пушит напрямую в ветки.

Что ограничено на бесплатном плане для приватных репо: **protected branches** и
обязательные review в PR. Это тариф GitHub Pro ($4/мес) или Team. Пока проект в двоих
обходимся без защиты ветки, но правило «в `main` только через PR» соблюдаем руками.

## Имена веток и коммитов

```
main                 всегда рабочее состояние
feat/<corner>        новая возможность    feat/gateway-balance
fix/<corner>         баг                  fix/queue-dlq
refactor/<corner>    реструктуризация     refactor/src-layout
docs/<corner>        только документация
```

Коммит: `<тип>: <что сделано>` в императиве, 72 символа на строку темы.

```
feat: add solution projection per captcha type
fix: requeue task on solver timeout
refactor: collapse 19 packages into src/captcha
docs: describe layer contracts
```

## Ежедневный цикл

```bash
git switch main && git pull --rebase
git switch -c feat/pow-friendly
# ... работа ...
make lint imports test
git add -A && git commit -m "feat: friendly captcha pow solver"
git push -u origin feat/pow-friendly
# PR -> squash merge в main
```

Если работаете вдвоём в одних и тех же файлах — сначала `git pull --rebase`, никогда
`git merge` из main в ветку. Конфликты в `pyproject.toml` и `solution.py` решаются дольше
всего, поэтому оба файла меняются отдельными PR.

## Что не попадает в репозиторий

`.gitignore` уже закрывает: `.env`, `.venv/`, `models-cache/`, `data/`, веса (`*.pt`,
`*.onnx`, `*.safetensors`), аудио, большие дампы (`fixtures/**/bulk/`), `uv.lock`
(лок ставим отдельно, если захотим воспроизводимость CI — тогда убираем строку из .gitignore).

Секреты — никогда в код: ключи API, прокси с паролями, S3-ключи. Всё через `.env`
(см. `.env.example`) и переменные окружения в CI/докере.

## Работа вдвоём: ветки и мерж

Модель — **trunk-based со короткими ветками**, как в большинстве нормальных команд.
Долгоживущей `develop` нет: она превращается в место, где живёт расходящийся код.

```
main                  всегда зелёный, всегда деплоится, прямой пуш запрещён правилом
 └── feat/pow-friendly       1-3 дня жизни, один смысл
 └── fix/queue-dlq
 └── docs/protocol
```

Почему не «две большие ветки и потом мерж»: если ты и напарник неделю пишете в разных
ветках, мерж превращается в отдельный день работы, а конфликты решаются вслепую. Короткая
ветка = маленький конфликт, который виден целиком.

### Ежедневный цикл (оба)

```bash
git switch main
git pull --rebase                 # обязательно rebase, не merge
git switch -c feat/<что-делаешь>

# ... работа ...

make lint imports test            # локально то же, что в CI
git add -A
git commit -m "feat: friendly captcha pow solver"
git push -u origin feat/<что-делаешь>
# открыть PR -> зелёный CI -> squash merge -> удалить ветку
```

### Правила, которые экономят нервы

1. **Ветка живёт не дольше 3 дней.** Не успеваешь — режь на две.
2. **Один PR = одна тема.** Не мешай «починил линт» и «добавил солвер».
3. **Перед пушем всегда `git pull --rebase`.** Никогда `git merge main` в свою ветку —
   иначе история превращается в спагетти из мерж-коммитов.
4. **В `main` только через PR**, даже если вас двое и PR пустой. Это точка, где второй
   человек видит, что изменилось, до того как оно уехало в прод.
5. **Squash merge**, не merge commit: в `main` один коммит на фичу, история читается.
6. **Кто мержит — тот и отвечает за зелёный CI после мержа.** Не «у меня локально работало».
7. **Конфликт разрешает автор ветки**, а не тот, кто мержит.

### Где будут конфликты

| файл | почему | как уменьшить |
|---|---|---|
| `pyproject.toml` | оба добавляют зависимости | разные PR, не смешивать с кодом |
| `domain/solution.py`, `domain/enums.py` | оба добавляют типы | сначала PR с типом, потом код на него |
| `docs/architecture.md` | оба правят дерево | правки дерева — только в PR, который меняет дерево |
| `docker-compose.yml` | оба добавляют сервис | сервис = отдельный PR |

### Ревью

PR читается целиком перед мержем. Минимальный чеклист ревьюера:

- [ ] изменение делает одну вещь, и она названа в заголовке;
- [ ] `make lint imports test` зелёные (это же проверяет CI);
- [ ] новые импорты не нарушают границы слоёв (`lint-imports` поймает, но лучше видеть);
- [ ] если появился новый капча-тип — обновлён runbook и `domain/`;
- [ ] если поменялось поведение API — обновлён `docs/protocol.md`;
- [ ] нет секретов, путей вида `C:\\Users\\...`, закомментированного кода.

### Окружение у обоих одинаковое

- Python пинится `.python-version` (3.14) — `uv` поставит его сам;
- `uv sync --extra dev` поднимает окружение без активации venv;
- всё запускается через `uv run ...` — venv-активация не нужна ни тебе, ни напарнику;
- `.vscode/` в репозитории: тема иконок, скрытие кэшей, ruff на сохранении — напарник
  получает такую же картину после клона;
- иконки папок живут в `.vscode/settings.json` (workspace) — работают у обоих, личные
  клоны из user settings внутри этого репозитория перекрываются, и это ожидаемо.

### Что делать, если что-то сломалось у напарника

1. `git log --oneline -5` — что он залил;
2. `git fetch && git switch main && git pull --rebase` — повторить у себя;
3. если падает только у него — почти всегда окружение: `uv sync --extra dev` заново,
   `rm -rf .venv` если совсем странно;
4. если падает у обоих — баг в `main`, чинится отдельной веткой `fix/`, не откатом.

## CI

`.github/workflows/ci.yml`: ruff → архитектурные контракты (`lint-imports`) → тесты
`tests/domain` и `tests/solvers/pow`. Тяжёлые CV-тесты подключаются отдельным job,
когда сойдёмся на образе с torch.

## Если что-то пошло не так

```bash
git status                  # что изменено
git diff --stat             # насколько
git switch -- .            # выбросить правки в рабочей копии
git restore --staged .     # снять со stage
git reflog                 # что было до неудачного rebase
```

Опасные команды (`reset --hard`, `clean -fdx`, `push --force`) — только с пониманием,
что в них теряется. В общую ветку `main` — никогда.
