# Работа с репозиторием

Как устроен поток изменений, что проверяет CI и как обходимся без платного GitHub.

## 0. Один раз после клона

```bash
git clone git@github.com:<логин>/captcha.git && cd captcha
uv sync --extra dev        # окружение (venv активировать не нужно, всё через uv run)
make hooks                 # включает .githooks/pre-push — блок прямых пушей в main
gh auth status             # или git config user.name / user.email, если gh нет
```

`make hooks` делает ровно одно: `git config core.hooksPath .githooks`. Без него guard
не работает, и всё держится на дисциплине.

## 1. Флоу: от задачи до main

```
        ┌──────────────────────────────────────────────────────────────┐
        │  main — всегда зелёный, всегда деплоится                     │
        └──────────────────────────────────────────────────────────────┘
              ▲                                        │
              │ squash merge (кнопка в PR)             │ git pull --rebase
              │                                        ▼
        ┌─────────────┐    PR + CI    ┌──────────────────────────────┐
        │  pull request│◄────────────│ feat/<тема> (живёт 1-3 дня)  │
        └─────────────┘              └──────────────────────────────┘
              ▲                                        ▲
              │ ревью напарником                       │ push
              │                                        │
        ┌──────────────────────────────────────────────────────────────┐
        │ локально: make lint imports test                             │
        └──────────────────────────────────────────────────────────────┘
```

Пошагово:

1. **Взять задачу.** Ветка называется по смыслу: `feat/queue-dlq`, `fix/solution-cf_clearance`,
   `docs/workflow`. Одна ветка — одна тема, не «и заодно починил линт».
2. **Синхронизироваться перед стартом.**
   ```bash
   git switch main && git pull --rebase
   git switch -c feat/<тема>
   ```
3. **Работать маленькими коммитами.** `feat: ...`, `fix: ...`, `refactor: ...`, `docs: ...`.
   Коммит в императиве, 72 символа на строку темы, тело — только если нужно объяснить «почему».
4. **Проверить локально то же, что проверит CI.**
   ```bash
   make lint imports test
   ```
   Красный CI на PR — это не «потом поправлю», это стоп-сигнал.
5. **Пуш и PR.**
   ```bash
   git push -u origin feat/<тема>
   gh pr create --fill --web        # или кнопка в вебе
   ```
   Шаблон PR (`.github/pull_request_template.md`) сам подставит чеклист: одна тема,
   локальные проверки, обновлён ли runbook/protocol/architecture.
6. **Ревью.** Напарник читает PR целиком, комментирует по строкам. Минимум, что должно быть:
   понятно, что меняется, CI зелёный, нет секретов. Замечания — комментариями, а не «переделай».
7. **Мерж — squash.** В `main` один коммит на фичу, история читается как список изменений,
   а не как «40 коммитов wip». Кнопка **Squash and merge** в PR.
8. **После мержа:** ветку удалить (GitHub предложит), у себя
   ```bash
   git switch main && git pull --rebase && git branch -d feat/<тема>
   ```
9. **Срочный фикс в проде:** та же схема с веткой `fix/<что>`, только PR мержится сразу
   после зелёного CI, ревью — вторым человеком постфактум. Никаких «пушу в main, потом разберёмся».

## 2. Ветки и коммиты

```
main                 всегда рабочее состояние
feat/<corner>        новая возможность
fix/<corner>         баг
refactor/<corner>    реструктуризация без изменения поведения
docs/<corner>        только документация
chore/<corner>       ci, конфиги, зависимости
```

```
feat: add solution projection per captcha type
fix: requeue task on solver timeout
refactor: collapse packages into src/captcha
docs: describe layer contracts
chore(ci): pin python 3.14
```

## 3. CI: что проверяется

`.github/workflows/ci.yml` на каждый PR и пуш в main:

| шаг | что ловит |
|---|---|
| `uv sync --extra dev` | сломанный `pyproject.toml`, несуществующую версию пакета |
| `ruff check` | стиль, мёртвые импорты, неиспользуемые noqa |
| `lint-imports` | нарушение слоёв: домен потянул redis, солвер — адаптер |
| `pytest` | `tests/domain` + `tests/solvers/pow`; тяжёлые CV-тесты отдельным job позже |

`.github/workflows/guard.yml` — отдельный сторожевой workflow: если в `main` прилетел
коммит без связанного PR, он краснеет и пишет `::error::Direct push to main`.

## 4. Бесплатный GitHub: чего нет и чем компенсируем

На бесплатном плане в **приватном** репозитории недоступны protected branches, обязательные
ревью и обязательные статус-чеки. То есть GitHub не может физически запретить пуш в main.
Не платим — компенсируем четырьмя механизмами:

| чего нет на free | наша замена | уровень |
|---|---|---|
| запрет пуша в `main` | `.githooks/pre-push` блокирует локально | жёсткий, но обходится `--no-verify` |
| видимость нарушения | `guard.yml` красит прогон в красный | постфактум, зато видно обоим |
| обязательный review | правило «мержить только чужой PR» + шаблон PR с чеклистом | договорённость |
| обязательный зелёный CI | PR не мержится, пока CI красный | договорённость + красный крестик на виду |

Как это выглядит на практике:

```bash
$ git switch main && git commit -m "wip" && git push
pre-push: direct push to main is blocked.

  work on a branch and open a PR:
    git switch -c feat/<name>
    git push -u origin feat/<name>

  one-off override:
    ALLOW_MAIN_PUSH=1 git push
```

Обход на один раз: `ALLOW_MAIN_PUSH=1 git push` — для первого пуша пустого репо или
ночного отката. Если обходов стало больше одного в неделю, значит процесс неудобный, и это
повод править процесс, а не привыкать к обходу.

### Публичный репозиторий: та же защита, но бесплатно

На публичных репозиториях GitHub Free отдаёт всё, чего не даёт на приватных:

| что | на публичном |
|---|---|
| branch protection / rulesets | есть, бесплатно |
| require pull request before merging | есть |
| require approvals (1 из 2) | есть |
| require status checks (`checks`) | есть |
| block force-push, block deletion | есть |
| Actions minutes | без лимита (на приватном — 2000/мес) |
| code / secret scanning | бесплатно (на приватном — платно) |

То есть переключение на публичный репозиторий — это не костыль, а ровно тот инструмент.
Цена одна: **код видят все, и это необратимо**. GitHub индексирует публичные репозитории,
боты их скрейпят, форк живёт даже после того, как ты удалил репозиторий или сделал его
приватным. Вернуть приватность можно, но защиту на free-плане ты при этом снова теряешь.

Перед переключением проверил репозиторий на утечки:

```
.env под контролем версий      — нет, только .env.example
ключи в истории коммитов       — нет (grep по log -p: ни RSA, ни ghp_, ни sk-)
файлов в репозитории           — 308, секретов не найдено
```

Создать сразу публичным:

```bash
gh repo create captcha --public --source=. --remote=origin --push
```

Включить защиту (веб-интерфейс, 30 секунд):

```text
Settings → Rules → Rulesets → New branch ruleset
  Target: main
  ✔ Require a pull request before merging   (Required approvals: 1)
  ✔ Require status checks to pass           (check: "checks")
  ✔ Block force pushes
  ✔ Restrict deletions
```

То же через API, если лень кликать (имя чека должно совпадать с тем, что Actions показывает
в PR — при сомнениях подсмотреть в списке проверок и поправить):

```bash
gh api -X PUT "repos/{owner}/{repo}/branches/main/protection" \
  -f "required_status_checks[strict]=true" \
  -f "required_status_checks[contexts][]=checks" \
  -f "enforce_admins=true" \
  -f "required_pull_request_reviews[required_approving_review_count]=1" \
  -F "restrictions="
```

Оценка риска: репозиторий молодой, коммерческой ценности текст пока не несёт, зато реальный
ущерб от «кто-то случайно запушил в main» — есть, и он случается регулярно. Если проект дойдёт
до продаж, приватность вернётся вместе с GitHub Pro за $4/мес, а мы получим тот же функционал
за деньги — это дешевле, чем потерять день на разбор сломанного `main`.

### Если публичным делать не хочешь

1. **GitLab Free** — protected branches и required approvals на приватных репозиториях
   бесплатны. Перенос: `git remote add gitlab ... && git push gitlab main`, GitHub остаётся
   зеркалом.
2. **GitHub Pro, $4/мес на человека** — то же, что было бы бесплатно на публичном.
3. Продолжать с хуком, guard-воркфлоу и дисциплиной — рабочий вариант для двоих, но защита
   держится на согласии, а не на настройках.

## 5. Где будут конфликты

| файл | почему | как уменьшить |
|---|---|---|
| `pyproject.toml` | оба добавляют зависимости | отдельный PR на зависимость |
| `domain/enums.py`, `domain/solution.py` | оба добавляют типы | сначала PR с типом, потом код на него |
| `docs/architecture.md` | оба правят дерево | правки дерева — в PR, который меняет дерево |
| `docker-compose.yml` | оба добавляют сервис | сервис = отдельный PR |

Правило разрешения: **конфликт чинит автор ветки**, не тот, кто мержит. И всегда
`git pull --rebase`, никогда `git merge main` в свою ветку — иначе история превращается
в спагетти из мерж-коммитов.

## 6. Ревью: минимальный чеклист

- [ ] изменение делает одну вещь, и она названа в заголовке PR;
- [ ] `make lint imports test` зелёные (то же видно в CI);
- [ ] новые импорты не нарушают границы слоёв;
- [ ] новый капча-тип → обновлён `runbooks/` и `domain/enums.py`;
- [ ] менялось поведение API → обновлён `docs/protocol.md`;
- [ ] нет секретов, путей вида `C:\\Users\\...`, закомментированного кода.

## 7. Окружение у обоих одинаковое

- Python пинится `.python-version` (3.14), `uv` поставит его сам и не тронет системный;
- `uv sync --extra dev` поднимает окружение, активация venv не нужна;
- всё запускается через `uv run ...` — ни тебе, ни напарнику не надо помнить про `.venv`;
- `.vscode/` в репозитории: тема иконок, скрытие кэшей, ruff на сохранении, иконки папок —
  напарник получает такую же картину после клона;
- `make hooks` — обязательный шаг после клона, иначе pre-push не сработает.

## 8. Что не попадает в репозиторий

`.gitignore` закрывает `.env`, `.venv/`, `models-cache/`, `data/`, веса (`*.pt`, `*.onnx`,
`*.safetensors`), аудио, большие дампы (`fixtures/**/bulk/`), кэши линтеров и `.import_linter_cache/`.

Секреты — никогда в код: ключи API, прокси с паролями, S3-ключи. Всё через `.env`
(см. `.env.example`) и переменные окружения в CI/докере.

`uv.lock` сейчас в `.gitignore`. Когда захотим воспроизводимость в CI — убираем строку и
коммитим лок.

## 9. Первый пуш и доступ напарнику

```bash
gh repo create captcha --private --source=. --remote=origin --push
# или: git remote add origin git@github.com:<логин>/captcha.git && git push -u origin main
```

Доступ: репозиторий → `Settings` → `Collaborators` → `Add people`, роль **Write**.
На бесплатном плане приватный репозиторий с неограниченным числом коллабораторов — можно.

## 10. Если что-то пошло не так

```bash
git status                  # что изменено
git diff --stat             # насколько
git switch -- .             # выбросить правки в рабочей копии
git restore --staged .      # снять со stage
git reflog                  # что было до неудачного rebase
git log --oneline --graph -10
```

Опасные команды (`reset --hard`, `clean -fdx`, `push --force`) — только с пониманием, что
в них теряется. В `main` force-push — никогда.

Если падает только у напарника: `git fetch && git pull --rebase`, потом
`uv sync --extra dev`; если совсем странно — `rm -rf .venv` и синк заново.
Если падает у обоих — это баг в `main`, чинится веткой `fix/`, не откатом.
