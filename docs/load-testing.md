# Нагрузочное тестирование

Как получить цифры «сколько стек держит» и как их читать. Инструмент — `tools/load/`,
операторский: он не входит в дистрибутив `captcha`, ничего из `src/` его не импортирует.

Два процесса, запускаются раздельно:

| команда | что делает |
|---|---|
| `python -m tools.load.devstack` | поднимает на одной машине настоящий gateway (uvicorn, реальные PG/Redis-адаптеры) и N воркеров с фейковым солвером |
| `python -m tools.load.run` | генерирует нагрузку по протоколу 2captcha (`createTask` → `getTaskResult`) и печатает отчёт |

## 1. Что именно меряется

Всё клиентское, глазами драйвера:

| фаза | что это |
|---|---|
| `createTask` | POST `/createTask`, до последнего байта ответа |
| `getTaskResult` | каждый POST опроса, включая промежуточные `processing` |
| `create->ready` | от начала `createTask` до `status=ready` — сквозная задержка задачи |

Плюс счётчики: `created`, `ready`, `failed`, `solve_timeout`, `unfinished`, `dropped`,
`polls`, глубина очереди и тайм-бакеты.

Генератор **open loop**: он предлагает фиксированный `--rate` независимо от того, как быстро
отвечает сервер. Это принципиально — закрытая петля при насыщении просто начинает слать меньше
и прячет потолок. Когда срабатывает потолок одновременных задач (`--in-flight-max`, по
умолчанию `max(64, rate)`), новый сэмпл **отбрасывается и считается** в `dropped_overload`:
прогон, который не вытянул свой же темп, обязан это сказать, а не тихо превратиться в медленный.

Опрос результата — с бэкоффом: первый интервал `--poll-interval` (50 мс), дальше ×1.5 за опрос
(×2 на сетевой ошибке), потолок — `--poll-max-interval` (1 с). Дедлайн задачи —
`--solve-timeout` (180 с), после него задача идёт в `solve_timeout`, а не в ошибку сервера.

## 2. Как читать отчёт

Текстовый отчёт фиксированного формата — два прогона диффятся построчно. Единицы в тексте —
миллисекунды (кроме `create->ready` p50, который печатается как `2.50s`, если больше секунды),
в JSON — `*_ms`.

```
target    1000/s for 60s  type=text_captcha  cap=1000  url=http://127.0.0.1:8080
--------------------------------------------------------------------------------
phase                 n  rate/s       p50      p95      p99      max
createTask        60000  1000.0       2.1      9.4     22.0     90.0
getTaskResult     90000  1500.0       1.9      7.1     18.0     61.0
create->ready     59990              60.0    200.0    400.0    900.0
--------------------------------------------------------------------------------
outcome   created=60000 ready=59990 failed=5 solve_timeout=5 unfinished=0 dropped=0
```

Процентили — линейная интерполяция между ближайшими рангами (то же определение, что у
`numpy.percentile` по умолчанию), поэтому внешний инструмент по тому же сырому массиву даст те же
числа. Сырые сэмплы хранятся целиком: 15-минутный сок на 1k/s — это ~5 МБ на фазу.

Вердикты — короткие и без утешений, пороги фиксированные:

| строка | условие |
|---|---|
| `target missed` | `achieved / target < 0.95` — потолок окружения или насыщение gateway |
| `overload` | были `dropped` — стек не принял предложенный темп |
| `errors` | есть ошибки; печатается самая частая пара `фаза:код` |
| `unfinished` | задачи не успели за `solve_timeout` + 5 с дренажа и выброшены из e2e |
| `backlog` | пик лага лейна > 1000 записей — воркеры отстают |
| `clean` | ни одного из условий выше |

`--strict` превращает первые два в код возврата 2 (для CI/ночного сока).

**Пер-бакетная таблица** (`--bucket-sec`, по умолчанию 15 с) показывает дрейф: `rps` и
`e2e p95` по интервалам. Ровный сок — это когда она плоская. Растущий p95 при ровном rps —
утечка или насыщение БД/пула.

**Секция queue** печатается только при `--redis-url`: драйвер сам читает стримы и consumer-группу.

| поле | откуда | смысл |
|---|---|---|
| `xlen` | `XLEN <prefix>:stream:<lane>` | сколько всего записей в стриме |
| `lag` | `XINFO GROUPS` → `lag` | доставлено никому — вот где виден бэклог |
| `pending` | `XINFO GROUPS` → `pending` | доставлено, но не подтверждено — работа внутри воркеров |

Лейн берётся из `captcha.domain.catalog` по типу (`--lane` переопределяет). Имя группы —
`group:lane-<lane>`. Сэмплирование best-effort: упавший Redis портит секцию, но не прогон
(`sample_errors`).

JSON (`--json run.json`) содержит тот же отчёт машинно-читаемым, плюс полный `config` с
замаскированным `client_key` — прогон воспроизводим из своего же JSON.

## 3. Локальный стенд

`tools.load.devstack` поднимает в одном процессе настоящий gateway (`create_app`, uvicorn) и
настоящие воркеры `worker_http` — реальная consumer-группа, реальный state store, реальный
протокол. Подменён только вызов солвера: `LoadTestSolver` спит `--fake-latency-ms` +
джиттер и возвращает `text='load-test'`, не трогая сеть, модели, прокси и браузер.

Требования — вне процесса: Redis и Postgres с применёнными миграциями
(`python -m captcha.services.cli init-db`), плюс аккаунт с балансом для `--key`.
Аккаунты стенд не создаёт: `python -m captcha.services.cli create-account --name demo --balance 10`.

Стенд зануляет квоты, иначе сок упирается в них, а не в стек:
`RATE_LIMIT_CREATE_PER_MIN=0`, `MAX_ACTIVE_TASKS_PER_ACCOUNT=0`, `MAX_DAILY_TASKS=0`,
`MAX_DAILY_SPEND=0` (через `setdefault` — уже выставленные в окружении значения не
перетираются).

`--flush` удаляет `<prefix>:*` в той Redis-базе, на которую указали. Только throwaway-база:
по умолчанию выключено.

## 4. Прогон

```bash
# терминал 1: стенд (redis :6399, pg :55432 — любые свои)
PYTHONPATH=$PWD/src python -m tools.load.devstack \
    --type text_captcha --workers 4 --concurrency 1024 \
    --redis-url redis://127.0.0.1:6399/1 \
    --postgres-url postgresql+asyncpg://captcha:captcha@127.0.0.1:55432/captcha --flush

# терминал 2: нагрузка
PYTHONPATH=$PWD/src python -m tools.load.run \
    --url http://127.0.0.1:8080 --key <clientKey> --type text_captcha \
    --rate 500 --duration 120 --redis-url redis://127.0.0.1:6399/1 \
    --json runs/soak-01.json --label soak-01 --strict
```

`PYTHONPATH` обязателен: драйверу нужен `captcha.domain.catalog`, чтобы знать лейн.
Против развёрнутого compose — тот же `run` с `--url` реального gateway; ключ можно не
светить в истории, а положить в `LOAD_CLIENT_KEY`.

## 5. Границы

- Драйвер меряет только HTTP-фронт и очередь. CPU/GPU воркеров, RSS, GC-паузы — не его дело;
  для них Prometheus (`docs/operations.md`).
- Стенд держит gateway и воркеры в одном event loop: на высоких rate они мешают друг другу
  самим фактом соседства. Абсолютные цифры с ноутбука — не SLA, сравнивать прогоны между собой.
- Фейковый солвер не воспроизводит профиль реальных: ни сети, ни ML-инференса, ни браузера.
  Он проверяет транспорт, очередь, state и биллинг — не солверы.
- Живые прогоны против настоящего сайта/прокси этим инструментом не предусмотрены.

## 6. Тесты

```bash
PYTHONPATH=src pytest tests/load -q
```

Покрыто: конфиг и маскирование ключа, процентили/бакеты/тэлли, полный сценарий против
замоканного gateway (`respx`: ready, errorId, 500, connect error, перегрузка по cap,
solve timeout, progress), рендер отчёта и вердиктов, включение фейкового солвера в реестр.
Живой Redis/Postgres тестам не нужен.
